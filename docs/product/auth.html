Session Token Hashing

Why SHA-256, Not bcrypt

Design Decision
bcrypt is non-deterministic — bcrypt.hash("token") produces a different output each call (random salt embedded). You cannot do WHERE token = bcrypt.hash(cookieToken) — the hashes never match.

SHA-256 is deterministic, one-way, and uses Node.js built-in node:crypto. Session tokens already have ~192 bits of entropy (32-char random strings) — no salt needed.

Migration Warning
Existing sessions are invalidated on deploy — DB stores plaintext tokens; after deploy, lookups hash the cookie token but no existing row matches. Users are signed out once and must re-authenticate.

Rollback Warning: If code is reverted after deploy, DB contains hashed tokens but reverted code does raw-token lookups — no one can authenticate until the sessions table is cleared.

Implementation

typescriptsrc/server/lib/session-token.ts
import { createHash } from 'node:crypto'

export function hashSessionToken(token: string): string {
  return createHash('sha256').update(token, 'utf8').digest('hex')
}
