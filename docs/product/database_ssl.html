Database SSL Configuration

Tech Debt Encrypted in Transit

TLS is enabled in production, but certificate chain verification is disabled — a deliberate trade-off pending Prisma and Railway fixes.

Current Configuration

typescriptsrc/server/lib/prisma.ts — pool SSL
ssl: env.NODE_ENV === 'production' ? { rejectUnauthorized: false } : false,
What This Means
The production connection is TLS-encrypted — wire traffic is protected. However, the certificate chain is not verified. A MITM attacker on the network path could in theory present any certificate.

Why rejectUnauthorized Is False

Issue 1 — No Railway CA Bundle
Railway doesn't publish a CA bundle for managed Postgres. Their TCP proxy presents a certificate chain not in Node.js's default trust store. No ssl.ca PEM to pin. Railway staff confirm: skip strict verification for project-private connectivity.
Issue 2 — Prisma 7 Regression
@prisma/adapter-pg in 7.x stops trusting Railway-style chains that worked in Prisma 6.x, even with explicit pool options or sslmode=verify-full.

Tracking Issues

  • prisma/prisma#29060 — "Error opening a TLS connection: self-signed certificate in certificate chain"
  • prisma/prisma#27611 — root duplicate, adapter-pg SSL handling
  • prisma/prisma#29252 — PrismaPg connectionString fails on SSL-required DBs

Future Hardening

Flip back to strict verification once either condition holds:

Condition A — Prisma Fix
Prisma ships a fix for #29060 / #27611 in the 7.x line that restores 6.x behavior — and we upgrade to that version.
Condition B — Railway CA Bundle
Railway exposes a CA bundle for managed Postgres. Then add DATABASE_SSL_CA to src/server/config.ts.
typescripthardened config (when a CA is available)
ssl: env.NODE_ENV === 'production'
  ? { rejectUnauthorized: true, ca: env.DATABASE_SSL_CA }
  : false,

Common Failure Scenarios

UNABLE_TO_VERIFY_LEAF_SIGNATURE / SELF_SIGNED_CERT_IN_CHAIN
Cause: DB certificate signed by a private CA not in Node.js's default trust store. With rejectUnauthorized: false this no longer fails the handshake — it would resurface if strict verification is re-enabled prematurely.

Fix when a CA is available:
ssl: { rejectUnauthorized: true, ca: env.DATABASE_SSL_CA }
CERT_HAS_EXPIRED
Cause: DB SSL certificate has passed its expiry date.
Fix: Renew certificate on the database server. On Railway this is handled automatically.
ERR_TLS_CERT_ALTNAME_INVALID / Hostname Mismatch
Cause: Hostname in DATABASE_URL does not match the CN or SAN in the certificate. Common when using an IP address instead of a hostname.
Fix: Use the hostname (e.g., postgres.railway.internal) rather than a raw IP in DATABASE_URL.
Connection Refused / ECONNREFUSED with SSL Enabled
Cause: Database server not configured to accept SSL connections at all.
Fix: Enable SSL on the Postgres server (ssl = on in postgresql.conf). Railway Postgres has SSL enabled by default.

Verifying the Connection Is Encrypted

Even with rejectUnauthorized: false, the channel is still TLS-encrypted. Confirm with:

sql
SELECT ssl, version FROM pg_stat_ssl WHERE pid = pg_backend_pid();

If ssl is t, the connection is encrypted. The lost guarantee is whose certificate terminated the TLS, not whether TLS is present.

Local Development

No Action Needed
SSL remains disabled in development and test environments (ssl: false). Local Postgres instances typically don't have SSL certificates configured.
