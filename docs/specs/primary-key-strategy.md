# Primary Key Strategy: Migrate to BIGINT IDENTITY

**Status:** Proposed
**Last updated:** 2026-05-22
**Scope:** All 18 domain models in `prisma/schema.prisma`. Better Auth models (User, Session, Account, Verification) are out of scope — they remain text-managed.

## 1. Summary

**Recommendation:** Migrate the 18 domain models from `String @id @default(uuid()) @db.Uuid` (UUIDv4) to `BigInt @id @default(autoincrement())` backed by a Postgres `IDENTITY` column. The bigint PK stays internal — never exposed in URLs or API responses.

**Public-facing IDs:** Add a second column per externally-addressed model. Named user-facing entities (Guild, Character) get a unique `slug`. Unnamed entities exposed via deep links / share codes (GuildInvite, GuildMessage, TavernMessage, JournalEntry) get an opaque `publicId` (nanoid, 12 chars). Internal-only rows (HabitCompletion, M2M joins, reports) get neither — never URL-addressed.

**Why now:** The schema is small (~20 tables), production data is disposable test data, and the migration adds slug/publicId in the same pass instead of two breaking changes. Cost will never be lower.

**Terminology note:** The user-facing phrasing "BIGINT UNSIGNED AUTO_INCREMENT" is MySQL syntax. Postgres has no `UNSIGNED` types. The equivalent is `BIGINT GENERATED BY DEFAULT AS IDENTITY`, optionally constrained with `CHECK (id > 0)` if we care about positivity (we don't — `IDENTITY` starts at 1).

## 3. Why this matters in 2026

Several pieces of older PG/PK advice are stale as of May 2026. Worth knowing before deciding:

- **"UUIDs are always bad for PKs"** — held for random UUIDv4 (B-tree page splits, WAL amplification). UUIDv4 is what we use today, so the criticism applies. Sequential bigint avoids this entirely.
- **"Use BIGSERIAL"** — superseded. `BIGSERIAL` is Postgres-proprietary legacy syntax that secretly creates a sequence + `OWNED BY` link. SQL-standard `BIGINT GENERATED ALWAYS|BY DEFAULT AS IDENTITY` (PG 10+) is the preferred form: portable, cleaner dependency semantics, and `GENERATED ALWAYS` blocks the "manual insert collides with sequence" foot-gun.
- **"int4 saves significant disk vs int8"** — overstated. Postgres aligns row fields on 8-byte boundaries, so a lone `int4` PK gets padded to 8 bytes anyway. Real savings only when two `int4`s pack adjacently. Default to `bigint` for new PKs.
- **"Avoid hash indexes"** — stale since PG 10 (2017). They're WAL-logged and crash-safe now. Still rarely preferred over btree for equality, but no longer broken.
- **Prisma 7.6 still emits `SERIAL`/`BIGSERIAL`, not `IDENTITY`** — `prisma#4693` open since 2020. Workaround documented in §8.

## 4. Benefits of BIGINT IDENTITY (vs current UUIDv4)

- **Size:** 8 B vs 16 B per key. Multiplied across every FK column and every index, this is a meaningful index-cache-footprint reduction.
- **Insert locality:** Monotonic inserts always land at the right edge of the B-tree → no random page splits, less bloat, less WAL traffic, smaller vacuum cost.
- **Join performance:** Integer compare beats 128-bit compare. Cybertec measured ~2× faster joins on large tables.
- **Operability:** `id=42` is far easier to copy-paste, talk about, and search logs for than `id=8b2e0c1f-...`. Faster psql/DataGrip ergonomics.
- **No client-side dependency:** Database owns the sequence; clients never need to generate IDs.
- **No casting trap:** With UUIDs we already hit one (`AGENTS.md:184` — "Better Auth user IDs are `text`, NOT `uuid`"). With integer FKs to integer PKs, that whole class of error goes away.

## 5. Disadvantages / risks

- **Enumeration leak (theoretical):** Sequential IDs in a URL like `/guild/42` reveal row counts and growth rate. Addressed structurally by §6 — the bigint PK never leaves the server; external surfaces use `slug` or `publicId`.
- **Lost ability to generate IDs client-side:** UUIDs let an offline/optimistic client mint an ID before the server round-trip. Covenant is online-only and server-authoritative. Not relevant.
- **Single-sequence contention:** A `IDENTITY` sequence serializes inserts. At >10k inserts/sec/table this becomes visible. Our scale is single-tenant per user. Not relevant.
- **`BigInt` in the Prisma client — the largest practical gotcha:** Prisma surfaces `BigInt` columns as JavaScript `BigInt`, and `JSON.stringify` throws on `BigInt`. Two mitigations:
  - **Preferred:** `superjson` (or similar) on the tRPC transport. Verify the project already uses it; if not, wire it up.
  - **Fallback:** install a global `BigInt.prototype.toJSON = function () { return this.toString() }` at app boot. Crude but effective.
  - **Anti-pattern:** mapping `BigInt` to `Int` in the Prisma client (defeats the whole reason we picked bigint).
- **Prisma emits `BIGSERIAL`, not `IDENTITY`:** Functionally equivalent; cosmetic. Optional post-step in §8.7 converts the column. Skipping it is fine.
- **Migration churn:** 18 model declarations, 30+ FK columns, ~10 Zod validators, the seed script. Mechanical but tedious. Acceptable because there's no live data to preserve.

## 6. Public-facing IDs: slug and publicId

The bigint PK is internal. External surfaces (URLs, share codes, API responses meant for end users) use a second column. Two flavors, picked per model:

### 6.1 `slug` — for named, user-meaningful entities

| Entity | Slug scope | Example URL |
|---|---|---|
| Guild | global unique | `/g/dragon-slayers` |
| Character | per-user unique | `/u/yifan/c/aragorn` |
| Area, Objective, Habit, Task | per-user unique (optional — only if ever shared/linked) | `/o/learn-rust` |

Schema:

```prisma
model Guild {
  id        BigInt   @id @default(autoincrement())
  slug      String   @unique
  name      String
  // ...
}
```

Rules:
- `@unique` index. Lookup cost: one extra B-tree probe vs PK lookup. Negligible.
- Slug is *immutable* once published, or back it with a redirect table to handle renames without breaking external links. Default to immutable.
- Generated from `name` at create time with collision suffix (`dragon-slayers`, `dragon-slayers-2`, …). Run input through a denylist / profanity filter if the slug is globally visible (Guild yes; per-user Character no).
- Validation: `/^[a-z0-9](?:[a-z0-9-]{0,62}[a-z0-9])?$/` — lowercase, no leading/trailing dash, max 64 chars.

### 6.2 `publicId` — for unnamed entities exposed via deep link or share code

| Entity | Why exposed |
|---|---|
| GuildInvite | join code |
| GuildMessage | deep link to message (reply, report) |
| TavernMessage | same |
| JournalEntry | shareable read-only link (if/when added) |

Schema:

```prisma
model GuildInvite {
  id        BigInt   @id @default(autoincrement())
  publicId  String   @unique  // 12-char nanoid, generated app-side
  guildId   BigInt
  // ...
}
```

Generation strategy: **nanoid in app code**, not in the database. Reasons:
- No PG extension to install (Coolify-managed host; extension provisioning is a separate ops task).
- Prisma can populate the field via middleware / extension or via the create call directly.
- `pg_nanoid` extension exists but is not worth the dependency for our scale.

Suggested helper:

```ts
import { customAlphabet } from 'nanoid';
const alphabet = '0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz';
export const generatePublicId = customAlphabet(alphabet, 12);
// Collision space: 62^12 ≈ 3.2 × 10^21. Safe at our scale.
```

Apply via Prisma extension or call sites on create. Validation: `z.string().regex(/^[0-9A-Za-z]{12}$/)`.

### 6.3 Skip entirely (no slug, no publicId)

Internal rows never URL-addressed. Bigint PK never leaves the server, used only as FK and in internal joins:
- HabitCompletion
- CharacterClass, CharacterQuest, CombatEnemy
- GuildMember, GuildCampaign, GuildCampaignProgress
- GuildMessageReport, TavernMessageReport
- All implicit M2M join rows

### 6.4 Why nanoid over UUID for publicId

- 12 chars vs 36. URLs are nicer (`/i/aBc123XyZ7Qp` vs `/i/8b2e0c1f-3a4d-4f5b-9c0e-1d2e3f4a5b6c`).
- Opaque — does not leak creation time.
- Same collision safety at our scale (62^12 ≈ 3.2 × 10^21).
- No extension needed.

### 6.5 Lookup pattern

Routers accept slug or publicId externally, resolve to bigint internally, then use bigint for all subsequent joins:

```ts
// tRPC procedure
.input(z.object({ slug: z.string() }))
.query(async ({ input, ctx }) => {
  const guild = await ctx.db.guild.findUniqueOrThrow({
    where: { slug: input.slug },
    select: { id: true, name: true, /* … */ },
  });
  // use guild.id (BigInt) for any further work
});
```

## 7. Index best practices to adopt alongside (PG 18, 2026)

The PK migration is the right moment to also align on index conventions:

- **btree** remains the default for PKs and FKs — already the case.
- **Covering indexes (`INCLUDE`)** for read-hot paths where the query selects a small set of columns by an indexed key. Lets PG do an index-only scan without inflating the comparison key.
- **Partial indexes (`WHERE …`)** for skewed predicates. Candidates in our schema: `WHERE "deletedAt" IS NULL` (if we adopt soft delete), `WHERE status = 'active'`, etc.
- **BRIN** for append-only large tables where physical order tracks `createdAt`. Candidates: `JournalEntry`, `GuildMessage`, `TavernMessage`, `HabitCompletion`. BRIN is orders of magnitude smaller than btree on such tables.
- **`btree_gin` / `btree_gist`** for composite indexes mixing a scalar key with `jsonb`/`tsvector`/range types.

Stale advice we should explicitly stop following:
- "Avoid hash indexes" (WAL-safe since PG 10).
- "Always prefer int4 to int8" (alignment padding makes this a wash for lone columns).

## 8. Migration steps

This is the data-loss-acceptable path. We have only disposable test data; we will reset the database.

### 8.1 Schema edit (`prisma/schema.prisma`)

For each of the 18 domain models:

```diff
- id String @id @default(uuid()) @db.Uuid
+ id BigInt @id @default(autoincrement())
```

For every FK column referencing those models:

```diff
- characterId String @db.Uuid
+ characterId BigInt
```

Add `slug` to named entities (Guild, Character; optionally Area/Objective/Habit/Task if shareable):

```prisma
slug String @unique
```

Add `publicId` to externally-addressed unnamed entities (GuildInvite, GuildMessage, TavernMessage, JournalEntry):

```prisma
publicId String @unique
```

Leave the 4 Better Auth models (`User`, `Session`, `Account`, `Verification`) untouched. Their PKs stay `String @id`.

### 8.2 Zod schema updates

Audit and replace `z.uuid()` calls in:
- `src/shared/schemas/tasks.schemas.ts`
- `src/shared/schemas/objectives.schemas.ts`
- `src/server/routers/kill-record.router.ts`
- Grep the repo (`rg "z\.uuid|z\.string\(\)\.uuid"`) to catch any missed.

Replacement pattern depends on whether the input is an internal PK or an external slug/publicId.

**Internal PK (only used inside trusted server boundaries — see §8.3 stricter alternative):**

```ts
const idSchema = z.bigint().positive();           // superjson over tRPC
const idSchema = z.coerce.bigint().positive();    // string-form (URL params, raw fetch)
```

**External lookup by slug:**

```ts
const slugSchema = z.string().regex(/^[a-z0-9](?:[a-z0-9-]{0,62}[a-z0-9])?$/);
```

**External lookup by publicId:**

```ts
const publicIdSchema = z.string().regex(/^[0-9A-Za-z]{12}$/);
```

Prefer the slug/publicId schemas at router boundaries; reserve bigint schemas for internal helpers if used at all.

### 8.3 tRPC transport / serializer

Confirm `superjson` is wired into tRPC links. If not, add it. Without it, `BigInt` values will throw when serialized. Quick test: a procedure returning `{ id: 1n }` should round-trip.

If for some reason `superjson` is undesirable, the alternative is the global `BigInt.prototype.toJSON` patch applied once at app boot.

**Stricter alternative — keep BigInt server-only:** never return PKs in tRPC responses. `select` `slug` or `publicId` instead, expose only those externally. Avoids `BigInt` on the wire entirely. Slightly more verbose in routers but a cleaner boundary.

### 8.4 Public-ID generation helper

Create `src/server/lib/public-id.ts`:

```ts
import { customAlphabet } from 'nanoid';

const alphabet = '0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz';
export const generatePublicId = customAlphabet(alphabet, 12);
```

Wire into create paths for GuildInvite, GuildMessage, TavernMessage, JournalEntry — either via a Prisma client extension that auto-fills `publicId` on `create`, or by calling `generatePublicId()` at every create site.

Add a `src/server/lib/slug.ts` helper for slug generation + collision suffix (e.g., `slugify(name)` with retry-on-conflict).

### 8.5 Seed rewrite (`prisma/manual/seed-dashboard.sql`)

Current seed pre-generates ~60 UUIDs via `gen_random_uuid()` into arrays and indexes into them when inserting related rows. With `IDENTITY`, the database assigns IDs at insert time. Seed must also populate `slug` and `publicId` where applicable. Rewrite pattern:

```sql
WITH new_area AS (
  INSERT INTO "Area" (name, "userId") VALUES ('Health', $1) RETURNING id
)
INSERT INTO "Objective" (name, "areaId")
SELECT 'Sleep 8h', id FROM new_area;
```

Or, simpler: do the inserts in a procedure and capture each `RETURNING id` into a local variable.

### 8.6 Push the schema

Per `AGENTS.md:77-78`:

```bash
pnpm prisma db push --force-reset --accept-data-loss
```

This drops the database and recreates it from the new schema. `--accept-data-loss` is required because column types are changing. Run it deliberately — the warnings are real, the action is irreversible without a backup.

### 8.7 (Optional) Convert SERIAL → IDENTITY

Prisma will have emitted `BIGSERIAL`. To upgrade to SQL-standard `IDENTITY` (cosmetic; both work):

```sql
ALTER TABLE "Habit" ALTER COLUMN id DROP DEFAULT;
DROP SEQUENCE "Habit_id_seq";
ALTER TABLE "Habit" ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY;
-- repeat for each table
```

Skip this step unless we have a specific reason to align with the SQL standard. `BIGSERIAL` works fine.

### 8.8 Re-seed

```bash
pnpm prisma db seed
# or psql -f prisma/manual/seed-dashboard.sql
```

### 8.9 Regenerate client and typecheck

```bash
npx prisma generate
pnpm typecheck
```

Fix any callsites that assumed `id: string`. Phase 1 exploration found none outside the Zod schemas already covered in §8.2.

### 8.10 Smoke test

Log in → create a Habit → list habits. The DB row should have an integer PK; the JSON response should carry it (as a string under `superjson`, or as a number-string).

## 10. Out of scope

- Changing Better Auth model PKs. They're externally managed and intentionally text.
- Production data migration. Test data only; reset is fine.
- Sharding, replication topology, distributed ID generation.
- Slug-rename / redirect table. Spec defaults to immutable slugs; revisit if user-renamable slugs become a product requirement.
- Soft-delete conventions, audit columns, or schema-wide refactors — out of scope here, even though the migration touches every model.
